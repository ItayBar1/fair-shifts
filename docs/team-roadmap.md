## חלוקת העבודה המומלצת

מומלץ להשתמש ב־GitHub Issues וב־Project לניהול משימות, וב־memory להקשר ולמסירה בין סשנים. זוהי הצעה להתייעצות; טרם נוצרו Issues או הוקצו בעלים.

כל Issue יתאר תוצאה שאפשר להדגים, עם הנתונים, השירות, הממשק והבדיקות הנדרשים לה. הוא יכלול שלב וסיפורי משתמש, תרחישי קבלה, תלות ב־Issues אחרים, בעלים אחד, קבצים/חוזים משותפים ותנאי סיום. כשמשימה גדולה, מפצלים אותה לתוצאות עסקיות קטנות, ולא לכרטיסי ״שרת״ ו״מסך״ המנותקים זה מזה.

חלוקה ראשונית אפשרית לשני אנשים: אחד מוביל את תיקוני הביצוע והבקשות, והשני את התזכורות והתפעול. את השלמות התכנון/ייבוא מחלקים לפי קבצים ותלויות. לפני תחילת כל משימה קובעים בעלים ומעדכנים את הלוח; אחרי מיזוג בודקים שהמשימות התלויות עדיין נשענות על חוזים תקפים.

קבצים משותפים מועדים להתנגשות: `src/server/actions.ts`, ‏`src/server/state.ts`, ‏`src/server/validation.ts`, סכמת המסד ומיגרציות. מתאמים מראש שינויי חוזים, ומשלבים מיגרציות בסדר אחד. כל מפתח ממשיך לפתח את המסלול שבאחריותו מקצה לקצה. אין צורך בפיצול היישום לשירותים.

## ענפים, בדיקות ופרסום

הוראת המשתמש: מעתה עובדים בענף ייעודי לכל משימה; העבודה הפעילה הועברה ל־`codex/import-restoration`. מגבים את ענף המשימה באמצעות commit ו־push, ופותחים PR לשילוב ב־main. Husky ממשיך לבדוק את מלוא תוכן ה־commit בתוך Docker. המפתח המצטרף צריך להתקין את ה־hook אחרי clone לפי ה־README.

מומלץ להגן על main עם PR, אישור אחד של המפתח השני ובדיקות CI נדרשות, ולחסום force push. אלה הגדרות מומלצות, שטרם הוחלו במאגר. [תיעוד GitHub להגנת ענפים](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

כיוון השחרור המאושר הוא פריסה אוטומטית כאשר שינוי נכנס ל־main, לאחר מעבר הבדיקות. מיזוג PR יוצר שינוי ב־main ומפעיל את אותו מסלול. בדיקות PR ימשיכו לרוץ לפני מיזוגו. אין עדיין pipeline לפריסה פעילה.

מסלול הפריסה המוצע:

1. CI ב־Docker בודק את גרסת main המיועדת לפריסה ובונה תמונות app/worker מזוהות לפי commit.
2. פריסה אחת בכל פעם, עם סודות סביבת ההפעלה מחוץ למאגר. אין לעצור פריסה באמצע migration בגלל push חדש.
3. לפני שינוי מסד: גיבוי מאומת ובדיקת התאמה לגרסה הקודמת; migration מבוקרת ותיעוד מגבלות החזרה.
4. העלאת האתר והעובד מאותה גרסה, בדיקת בריאות ותהליך קצר אחרי הפריסה. תקלה מאפשרת חזרה לתמונה קודמת כאשר המסד תואם; migration שאינה הפיכה דורשת נוהל שחזור נפרד.

GitHub Actions תומך בסביבות ובסדרה של פריסות באמצעות concurrency; יש להגדירם כחלק מ־R14. [תיעוד פריסה](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments).

בשרת Ubuntu מתוכננים קונטיינרים לאתר, לעובד, ל־PostgreSQL ול־cloudflared, עם אחסון מסד מתמיד והפרדת סודות. Tunnel ינתב את שם המתחם לשירות האתר באמצעות חיבור יוצא מהשרת. Compose הנוכחי מכיל סודות לפיתוח סינתטי ואינו תצורת production. [תיעוד Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/).

## מתי אפשר לשחרר

אפשר להכין סביבת staging עם נתונים סינתטיים לפני השלמת כל יכולות המוצר, כדי לתרגל תהליך פריסה על Ubuntu, חיבור Tunnel והחלפת גרסאות. גם לסביבה זו נדרשות תצורת הפעלה וסודות מתאימים; לא מעלים את Compose המקומי כפי שהוא לאינטרנט.

שימוש production בנתוני אמת כפוף להכרעה 151: מלוא הגרסה ותנאי ההפעלה לפני הפיילוט. נדרשים סגירת הדרישות ובדיקות הקבלה, מחיקה מלאה, שחזור שהודגם, חיבורי Google/Brevo/Drive עם חשבונות בדיקה, נתוני יחידה מאומתים ותנאי ההפעלה שבאפיון. אחרי השער מתחיל פיילוט עם שני האחראים.

אין כעת תאריך שחרור מבוסס. אחרי פירוט ה־Stories, חלוקת בעלות וקביעת זמינות שני המפתחים אפשר לתת אומדן. השמטת יכולות כדי להוציא גרסת production מצומצמת תהיה שינוי היקף שדורש הכרעה מפורשת.
